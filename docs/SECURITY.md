# تفعيل حماية FORAGE

التعديلات في المشروع لا تغيّر قاعدة Supabase المستضافة تلقائيًا. لم يتم نشرها على السيرفر أو بناء نسخة جديدة بعد.

## خطوات النشر

1. خذ نسخة احتياطية من قاعدة Supabase وبيانات الورشة. اختبر أولًا في مشروع تجريبي بنفس البيانات؛ قواعد التحقق الجديدة ترفض السجلات القديمة غير المطابقة بدل تغييرها بصمت.
2. طبّق الملفين بالترتيب في SQL Editor، بعد migrations القديمة الموجودة أصلًا:
   - `supabase/migrations/202611170001_security_hardening.sql`
   - `supabase/migrations/202611170002_validate_workshop.sql`
   كلا الملفين داخل transaction وقابل لإعادة التشغيل. لا تعِد تشغيل الملفات القديمة بعدها لأنها قد تستبدل قواعد الحماية.
   بعدهما طبّق `supabase/migrations/202611170003_owner_maintenance.sql`. هذا يمنح `owner@younes.com` صلاحية المدير الكاملة ويفتح له فقط صفحة الحذف النهائي.
3. انشر مجلد `supabase/functions/admin-create-user` كاملًا، بما فيه `validation.mjs`، بعد تطبيق SQL. باستخدام Supabase CLI المرتبط بمشروعك:
   ```sh
   supabase functions deploy admin-create-user
   ```
4. في إعدادات Supabase Auth: عطّل التسجيل العام للحسابات؛ الإنشاء عبر المدير فقط. اضبط كلمات المرور على 12 حرفًا على الأقل مع حروف صغيرة وكبيرة وأرقام. راجع حدود محاولات تسجيل الدخول، وفعّل فحص كلمات المرور المسرّبة إن كان متاحًا في خطتك. لا تفعّل CAPTCHA دون إضافة تدفقه للتطبيق أولًا.
5. حدّث الأجهزة إلى بناء جديد من هذه الشيفرة. المزامنة تستخدم الآن `get_forage_workshop` و`save_forage_workshop`؛ الإصدارات القديمة للموظفين ستُرفض لحماية البيانات. اختبر مديرًا، عاملًا، مسؤول التحقق، وزائرًا على جهاز معتمد وغير معتمد قبل تعميم النسخة.
6. بعد رفع التعديلات إلى GitHub، يعمل فحص الأمان مع التغييرات وأسبوعيًا من الفرع الافتراضي. فعّل إشعارات فشل Actions لحساب المسؤول. الملف المحلي وحده لا يشغّل هذه المراقبة.

## الحماية المضافة

- تسجيل الدخول لا يستطيع منح جهاز العامل الثقة لنفسه. تسجيل الجهاز وقراءة بيانات الورشة يتطلبان موافقة السيرفر. تعديل الأدوار والأجهزة مقصور على المدير.
- لا تتحول حسابات التسجيل العام إلى حسابات ورشة فعالة عبر بيانات يختارها المستخدم. إنشاء الحسابات مضبوط من السيرفر مع حد 10 طلبات/دقيقة لكل مدير؛ طلبات الأجهزة 10/ساعة لكل حساب.
- قواعد RLS ودوال السيرفر تتحقق من الدور والجهاز وحالة الحساب. صفحات المدير مخفية عن غيره مع تحقق مستقل على السيرفر؛ تغيير الدور أو الصفحات ينهي الجلسة في دورة المزامنة التالية عند الاتصال.
- بيانات الأجور والمدفوعات لا تُرسل لغير المدير، ولا يستطيع تعديلها عبر المزامنة. تُراجع الحقول والأحجام والأنواع والكميات وتوازن الإنتاج وحالة التحقق على السيرفر.
- جلسة Supabase محفوظة في مخزن النظام الآمن. تُزال الجلسة القديمة من التفضيلات. كلمات المرور المحلية تستخدم PBKDF2 مع salt؛ Supabase يدير تجزئة كلمات مرور السحابة. لا نخزن كلمات المرور قابلة لفك التشفير.
- الحسابات الجديدة تستخدم كلمة مرور قوية؛ أزيل اختيار النمط من إنشائها. تسجيل الدخول بالنمط للحسابات القديمة باقٍ للتوافق: على المدير استبدال كلمات مرور هذه الحسابات في Supabase Auth.
- التطبيق الأصلي يعرض نصوص Flutter، ولا يشغّل HTML/JavaScript من بيانات المستخدم. مدخلات الحسابات والنصوص تُراجع، وروابط APK مقيدة بمستودع المشروع وHTTPS. هذا لا يُعد تدقيقًا لواجهة ويب مستقبلية.
- استعلامات SQLite تستخدم المعاملات `?` و`whereArgs`. أسماء الجداول الديناميكية في الترحيل والمزامنة من قوائم ثابتة. لا تُركّب قيم المستخدم داخل SQL.
- مفتاح Supabase العام قابل للرؤية بطبيعة تطبيقات الهاتف؛ الحماية من الصلاحيات على السيرفر. يمنع التطبيق تمرير مفتاح `service_role` أو `sb_secret` مكان المفتاح العام. الأسرار الخاصة تبقى في إعدادات Edge Functions وGitHub Secrets.
- أُزيلت `cupertino_icons` غير المستخدمة، وثُبّت إصدار مكتبة Supabase الخاصة بالسيرفر. فحص OSV يغطي إصدارات Pub المقفلة؛ عدم وجود نتائج لا يضمن عدم وجود ثغرات غير مسجلة. الإصدارات المقيدة بسبب توافق image/archive لم تُرفع عشوائيًا.

## المراقبة وحدودها

افتح **Équipe → Sécurité** بحساب المدير: آخر 100 حدث، مع تحديث كل 30 ثانية أثناء فتح الصفحة. يُسجَّل إنشاء الحسابات وتغيير الصلاحيات وحالات الأجهزة والدخول وتجاوز حدود الطلبات. المستخدمون لا يستطيعون حذف السجل أو كتابة أحداث مزورة فيه مباشرة.

محاولات كلمة المرور الفاشلة وطلبات API المرفوضة تُراجع في سجلات Supabase Auth/API. العمليات التي يتراجع عنها PostgreSQL لا تترك حدثًا داخل المعاملة المتراجَع عنها. لا يوجد إرسال تنبيهات بريدية فورية أو مراقبة بشرية مستمرة في هذه التعديلات؛ فحص GitHub الدوري مستقل عن سجل التطبيق.

ملاحظات للنشر: MFA ليس مفروضًا هنا؛ يحتاج تسجيل عوامل وتدفق تحقق داخل التطبيق. معرّف الجهاز إثبات تثبيت عشوائي وليس شهادة عتاد. البيانات التشغيلية المشتركة ما زالت تُزامن كملف واحد، فلا تعادل الصفحات صلاحيات قراءة منفصلة لكل حقل؛ الأجور والمدفوعات وحدها مفصولة في القراءة بهذه النسخة. كاش SQLite المحلي غير مشفر، ولا يمكن سحب البيانات التي سبق تنزيلها من جهاز غير متصل. حدّث حماية الأجهزة نفسها. المزامنة القديمة للملف الكامل تحتاج لاحقًا معاملات لكل عملية وحل تعارضات التحرير المتزامن.

```sh
flutter analyze
flutter test
node tools/security/check-secrets.mjs
node tools/security/check-dependencies.mjs
node --test tools/security/validation.test.mjs
npm install --prefix .security-tools --ignore-scripts @electric-sql/pglite@0.5.16
node tools/security/database.test.mjs
```

اختبارات قاعدة البيانات تعمل على PostgreSQL محلي مع حسابات وهمية ولا تتصل ببيانات الإنتاج. اختبر النشر الفعلي وصلاحياته أيضًا في مشروع Supabase تجريبي.
